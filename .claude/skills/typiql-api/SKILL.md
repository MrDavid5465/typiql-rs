# Building on typiql

typiql turns plain Rust structs into a full GraphQL CRUD API at compile time.
One `#[typiql_type]` struct, listed in `typiql_schema!`, gets list and get queries
with a filter argument for each field and operator, sorting, paging, a page-info
query, add/update/remove mutations, a change subscription, and batched relation
fields. Storage is pluggable: JSON file, DuckDB, SQL Server, MongoDB or LDAP.
Clients can't tell which adapter serves a type.

**The rule: data that is read or written CRUD-style is a typiql type.** This
covers anything you list, get, add, update, remove or subscribe to. Don't
write a resolver that does what the generated API already does. Don't keep a
second store next to the adapter, such as a hand-rolled JSON file, a
`static Mutex<Vec<_>>` or a separate DB pool. Only write a custom resolver for
the things in [Custom resolvers](#custom-resolvers-the-narrow-exception), and
even then go through typiql's adapter and helpers.

## Setting up a new app

### Cargo.toml

```toml
[dependencies]
# The crate is published as `typiql-core`, but the macros expand to `::typiql::…`
# paths. It MUST be renamed to `typiql`.
typiql = { package = "typiql-core", git = "https://github.com/MrDavid5465/typiql-rs" }
typiql-adapter-json = { git = "https://github.com/MrDavid5465/typiql-rs" }
# Side-by-side clone instead: path = "../typiql-rs/crates/typiql-core" (and …/typiql-adapter-json)

# All four are required. The macro output names ::async_graphql, ::tokio,
# ::serde and ::serde_json directly, so a transitive dependency isn't enough.
async-graphql = "7"
tokio = { version = "1", features = ["rt-multi-thread", "macros", "net"] }
serde = { version = "1", features = ["derive"] }
serde_json = "1"

axum = "0.8"                                            # same major version typiql-core uses
tower-http = { version = "0.6", features = ["cors"] }   # only if the frontend is served from another origin
```

If `async-graphql` or `tokio` is missing, you get `could not find async_graphql in
the list of imported crates` and `cannot find attribute graphql`.

### Types and schema

```rust
// src/types.rs
use typiql::typiql_type;

#[typiql_type]
pub struct Project {
    #[typiql(key)]
    pub id: String,
    pub name: String,
    pub is_default: bool,
}
```

```rust
// src/main.rs
// #![recursion_limit = "256"]   // add once the schema grows. See "Gotchas" below.
use std::{collections::HashMap, sync::Arc};
use typiql::{typiql_schema, AdapterMap, TypiQLAdapter};
use typiql_adapter_json::JsonAdapter;

mod types;
use types::*; // typiql_schema! refers to the generated ProjectQuery/ProjectMutation/… by bare name,
              // so every listed type's module must be glob-imported (or in this module).

// Types; extra Query roots; extra Mutation roots; extra Subscription roots.
// Trailing sections are optional: `typiql_schema!(Project, Task);` is valid.
typiql_schema!(Project; AppQuery; AppMutation);

#[derive(Default)] pub struct AppQuery;       // custom roots must be Default + #[Object]
#[async_graphql::Object] impl AppQuery { async fn healthy(&self) -> bool { true } }
#[derive(Default)] pub struct AppMutation;
#[async_graphql::Object] impl AppMutation { async fn ping(&self) -> bool { true } }

#[tokio::main]
async fn main() {
    let data_dir = std::env::var("DATA_DIR").unwrap_or_else(|_| "data".into());

    let mut adapters: AdapterMap = HashMap::new();
    adapters.insert("default", Arc::new(JsonAdapter::new(&data_dir)) as Arc<dyn TypiQLAdapter>);
    let schema = build_typiql_schema(adapters); // generated by typiql_schema!

    let app = axum::Router::new()
        .nest("/typiql", typiql::typiql_router(schema, "/typiql/graphql"))
        .layer(tower_http::cors::CorsLayer::permissive()); // dev only; or proxy /typiql from the frontend dev server

    let listener = tokio::net::TcpListener::bind("127.0.0.1:4000").await.unwrap();
    axum::serve(listener, app).await.unwrap();
}
```

`typiql_schema!` generates `TypiQLQuery`, `TypiQLMutation`, `TypiQLSubscription`,
`build_typiql_schema(adapters)` and `typiql_schema_builder(adapters)`. Use the
builder when you need to add `.data(...)` or extensions before `.finish()`.

The router serves `POST /graphql` (queries, mutations and subscriptions) and
`GET /playground` under the prefix you nest it at. The second argument is the
absolute GraphQL URL the playground calls.
- `typiql::typiql_router(schema, path)` is shorthand for
  `typiql::TypiQLRouter::new(schema, path).build()`.
- Use `TypiQLRouter` directly only when the app has users:
  `TypiQLRouter::new(schema, path).with_user::<MyUser>().build()`. See the
  README's "Optional auth".

### Adapters

- **Choosing one**: every type uses the `"default"` entry unless it declares
  `#[typiql_type(adapter = "name")]`, which needs a matching
  `adapters.insert("name", …)`. If an entry is missing, the server panics when
  the schema is built, and the panic names the type.
- **`JsonAdapter::new(dir)`**: one file, `<dir>/data.json`. Each type is a
  top-level table named after its plural snake_case name (`projects`, `tasks`).
  - The directory is created on first write.
  - The whole file is rewritten atomically on every write. That suits app and
    config data, but not high-volume rows.
  - Keep `dir` outside anything a dev-server file watcher watches.
  - Give logs their own `JsonAdapter` on a separate directory.
- **`typiql_adapter_duckdb::DuckDbAdapter::new(path)`**: for large or
  append-heavy data. Its `bundled` default feature compiles DuckDB from source
  (~20 minutes the first time).
- **MSSQL, Mongo, LDAP**: see the README.

## Declaring types

```rust
#[derive(async_graphql::Enum, Clone, Copy, PartialEq, Eq, Debug, Default,
         serde::Serialize, serde::Deserialize)]
pub enum Status { #[default] Todo, Doing, Done }

#[typiql_type]
pub struct Task {
    #[typiql(key)]
    pub id: String,              // or an integer type: adapters assign max + 1
    pub project_id: String,
    pub title: String,
    pub status: Status,
    pub position: i64,
    pub due: Option<String>,
    pub tags: Vec<String>,
}
```

- **Derives**: `#[typiql_type]` adds `SimpleObject`, `Serialize`, `Deserialize`,
  `Clone` and `Debug`. Don't derive them yourself.
- **Key**: mark exactly one field `#[typiql(key)]`.
  - Clients never send it. It isn't in `TaskInput`, and the adapter generates
    it (a UUID for `String`, max + 1 for integers).
  - Never generate keys yourself.
  - `#[typiql(key, input)]` lets clients supply it, for natural keys only.
- **Field types**:
  - Scalars (`String`, `bool`, integers, floats), `Option<_>` and `Vec<scalar>`.
  - Enums with the derives shown above.
  - Nested structs deriving `async_graphql::SimpleObject` +
    `async_graphql::InputObject` + serde, with `#[graphql(input_name = "XInput")]`.
  - Every non-key field must implement `Default`. A missing value reads back as
    the default.
- **Missing fields are not an error**: there's no "required field" validation on
  `add`. Omitted non-`Option` fields are stored as their default (`""`, `0`,
  `false`, `[]`, the enum's `#[default]`).
- **Names are permanent**: the type name fixes both the GraphQL names and the
  storage table name. Renaming a type orphans its existing rows.
- **Storage names**: `#[typiql(data_name = "col")]` changes only the storage
  name. GraphQL still uses the Rust field name.

## Generated API reference

For `Task` (Rust snake_case → GraphQL camelCase; plural = `simple_plural` of the
snake_case name):

| Kind | GraphQL |
|---|---|
| list | `getTasks(<filters>, _orderBy, _orderBy_desc, _start, _limit): [Task!]!` |
| count/paging | `getTasksPageInfo(<same args>): PageInfo!` → `{ totalResults page totalPages }` |
| get one | `getTask(<same args>): Task` (first match after sorting; `null` if none) |
| add | `addTask(values: TaskInput!): Task!` |
| update | `updateTask(id: String!, update: TaskInput!, _upsert: Boolean): Task` (`null` if no such row) |
| remove | `removeTask(id: String!): Task` (returns the removed row, `null` if none) |
| subscribe | `taskChanged(id: String): TaskChanged!` → `{ operationName value { … } }` |
| opt-in bulk | `addTasks(items: [TaskInput!]!)`, `updateTasks(<filters>, update: TaskInput!)`, `removeTasks(<filters>)`, each returning `[Task!]!` |

- **`update`/`remove` arguments**: they're named after the key field in
  camelCase. A key field `slug` gives `updateTask(slug: …)`. The integer-key
  type is `Int!`.
- **The subscription's filter argument** is always called `id`, whatever the
  key is called.
- **Pluralizer**: it's a naive rule, and it applies to the last word of the
  snake_case name.
  - Words ending `s`/`x`/`z` add `es`: `Status` → `getStatuses`.
  - Words ending in a consonant + `y` take `ies`: `Category` → `getCategories`,
    `Entry` → `getEntries`.
  - Everything else adds `s`: `Recurring` → `getRecurrings`,
    `Person` → `getPersons`, `Batch` → `getBatchs`.
  - When unsure, check the playground's schema docs. Don't guess.
- **Acronyms**: avoid them in type names. `HTTPLog` snake-cases to `h_t_t_p_log`.
- **Filter suffixes** (these are the C# typiql names): `field` (equals),
  `field_not`, `field_in`, `field_notIn`.
  - Numbers and strings also get `field_gt`, `_gte`, `_lt` and `_lte`.
  - Strings also get `_startsWith`, `_endsWith`, `_contains` and their `_not…`
    forms (case-insensitive).
  - `bool`, enums and nested objects get only `field` and `field_not`.
  - `Vec<scalar>` gets `field_anyEq` and `field_anyNe`.
  - All arguments are ANDed.
  - It's `_not`, not `_ne`, and `_notIn`, not `_not_in`.
- **Sorting**: `_orderBy`/`_orderBy_desc` take comma-separated GraphQL field
  names (`"projectId,position"`). Ties break by key.
- **Input naming**: `TaskInput` fields are camelCase over GraphQL (`projectId`).
  In Rust they're snake_case fields of type `async_graphql::MaybeUndefined<T>`.
  Build them with struct literals. Don't deserialize camelCase JSON into them:
  serde expects `project_id` and silently ignores unknown keys.
- **Update semantics** (`MaybeUndefined`):
  - An omitted field is left untouched.
  - An explicit `null` clears the field.
  - A value sets it.
  - Never write a "patch" resolver. This is already a patch.
- **Upsert**: `_upsert: true` creates the row if the key doesn't exist.
- **Subscriptions** are served over HTTP multipart. There's no WebSocket
  endpoint.
  - POST the subscription with
    `Accept: multipart/mixed; boundary="graphql"; subscriptionSpec="1.0"`.
  - Each part is `{"data":{"taskChanged":{…}}}`. A `{}` heartbeat arrives every
    second.
  - `operationName` is `"add"`, `"update"` or `"remove"`. `value` is the full
    row (the removed row, for remove).
  - Pass `id` to watch one record.
  - Each open subscription holds one browser connection. To listen to many
    types, put several aliased `xChanged` fields in one operation (see
    [One subscription for every type](#one-subscription-for-every-type-live-updates-hub)).
- **Batching**: several mutations can go in one request with GraphQL aliases
  (`a: addTask(…) b: addTask(…)`).

### Declaring the surface: `ops(...)`

Without `ops(...)`, a type gets `get, list, add, update, remove, subscribe`.
**`ops(...)` replaces that default, so it doesn't add to it.** To keep the
defaults and add a bulk operation, list them all:

```rust
#[typiql_type(ops(get, list, add, update, remove, subscribe, update_many))]
pub struct Task { /* … */ }
```

Each op takes options:
- `name = "…"` sets a custom GraphQL name.
- `filters(a, b)` (get, list and the bulk ops) narrows the filter arguments.
- `roles(...)`, `scope(...)` and `set(...)` are covered in the README's auth
  section.

A bulk update or remove with no filter is refused, so it can't touch every row.
Read-only type: `ops(get, list)`. Append-only: `ops(add, list)`.

## Relations: use them instead of manual joins

Never fetch a parent and then loop over it to query children, whether in a
resolver or on the client. Declare the relation once:

```rust
#[typiql_type]
pub struct Project {
    #[typiql(key)] pub id: String,
    pub name: String,
    // has-many: every Task whose project_id == self.id
    #[typiql(relation(local = "id", foreign = "project_id", order_by = "position"))]
    pub tasks: Vec<Task>,
}

#[typiql_type]
pub struct Task {
    #[typiql(key)] pub id: String,
    pub project_id: String,
    // has-one: the Project whose id == self.project_id
    #[typiql(relation(local = "project_id", foreign = "id"))]
    pub project: Option<Project>,
}
```

```graphql
{ getProjects { name tasks { title project { name } } } }
```

- **`local`, `foreign` and `op`**: `local` names a plain field of this struct,
  and `foreign` names a field of the target. Both use Rust field names. `op`
  defaults to `eq` and accepts any filter operator.
  - Use `value = …` instead of `local` to compare against a literal or
    `"@currentUser"`.
  - Repeat the attribute to add conditions (all must hold).
  - `order_by`, `order_by_desc`, `start` and `limit` sort and page a has-many
    relation, for example `order_by_desc = "created_at", limit = 5`.
- **What gets stored**: relation fields aren't stored and don't appear in
  `…Input`. Only the `local` field (`project_id`) is stored. Clients set the
  link by writing that field.
- **Batching**:
  - Has-one (`Option<T>`) is batched through a DataLoader across the whole
    query (no N+1).
  - Has-many (`Vec<T>`) runs one query per parent row. That's fine for normal
    page sizes.
  - To make a has-one free (joined into the parent's read) and sortable as
    `_orderBy: "project.name"`, give it a `data_name`.
- **Registration**: every relation target must be listed in `typiql_schema!`.
- **Mutual has-one**: two types with has-one relations pointing at each other
  need `Option<Box<T>>` on one side. `Vec` on one side is fine as is.
- **No cascades**: `removeProject` doesn't remove its tasks. Remove children
  explicitly (client-side, or with a `remove_many` op filtered by `projectId`).

### Aggregates before derived-view resolvers

For counts, sums or averages grouped by fields, declare an aggregate type
instead of writing a resolver:

```rust
#[typiql_type(aggregate = "Task")]
pub struct TaskCount {
    pub project_id: String,          // group-by fields
    pub status: Status,
    #[typiql(aggregate(count))]      // also count = "f", sum/avg/min/max = "f"
    pub tasks: i64,
}
// → getTaskCounts(projectId: "…") { status tasks }, read-only, filterable, sortable
```

## Custom resolvers: the narrow exception

A hand-written resolver goes in your extra Query or Mutation root. It's
justified only for behaviour the generated surface can't express, and usually
only when the user asked for that behaviour:

- **Cross-row invariants**, such as "exactly one project is the default" or
  "renumber positions when a task moves".
- **Side effects outside the store**, such as sending a notification, starting
  or controlling an external process, or calling a third-party API.
- **Derived or computed views** that aggregates and filters can't express.
- **Importing or parsing external formats** into typiql rows.

These are **not** reasons for a custom resolver:
- "I need several rows created in one round-trip." Use aliases, or `add_many`.
- "Update everything matching X." Use `update_many` with filters.
- "Filter by Y." Use the generated filter arguments; never fetch everything and
  filter in code.
- "Child rows with their parent." Use a relation.

### Writing one correctly

Use the typed helpers in `typiql::`. They pick the type's adapter, complete new
rows to full shape and deserialize the results:

| Helper | Use |
|---|---|
| `resolve_list::<T>(ctx, filters)` | all rows matching `Vec<FieldFilter>` (empty = every row) |
| `resolve_query::<T>(ctx, ListQuery { filters, sort, skip, limit, key_field: T::key_field().into(), ..Default::default() })` | sorted/paged read |
| `resolve_add::<T>(ctx, input)` | insert from a `TInput` |
| `resolve_update::<T>(ctx, key, input)` | patch (MaybeUndefined semantics) → `Option<T>` |
| `resolve_remove::<T>(ctx, key)` | remove → `Option<T>` |
| `resolve_add_many::<T>(ctx, rows)` / `resolve_add_many_inputs::<T>(ctx, inputs, vec![])` | bulk insert |

**These helpers do NOT publish change events.** Only the macro-generated
mutations publish. A hand-written write that skips publishing is invisible to
every `xChanged` subscriber, so live UIs go stale until a refresh. Publish
once for each row you changed:

```rust
use async_graphql::{Context, MaybeUndefined, Object, Result};
use typiql::{FieldFilter, FilterOp, TypiQLBroker, TypiQLType};

#[derive(Default)]
pub struct AppMutation;

#[Object]
impl AppMutation {
    /// Cross-row invariant: exactly one project is the default.
    async fn set_default_project(&self, ctx: &Context<'_>, id: String) -> Result<Option<Project>> {
        let current = typiql::resolve_list::<Project>(ctx, vec![FieldFilter {
            field: Project::data_name("is_default").to_string(), // storage name, not camelCase
            op: FilterOp::Eq,
            value: true.into(),
        }]).await?;
        for p in current.into_iter().filter(|p| p.id != id) {
            let patch = ProjectInput { is_default: MaybeUndefined::Value(false), ..Default::default() };
            if let Some(v) = typiql::resolve_update::<Project>(ctx, p.id, patch).await? {
                TypiQLBroker::publish(ProjectChanged { operation_name: "update".into(), value: v });
            }
        }
        let patch = ProjectInput { is_default: MaybeUndefined::Value(true), ..Default::default() };
        let updated = typiql::resolve_update::<Project>(ctx, id, patch).await?;
        if let Some(v) = &updated {
            TypiQLBroker::publish(ProjectChanged { operation_name: "update".into(), value: v.clone() });
        }
        Ok(updated)
    }
}
```

- **`FieldFilter`**: `field` is the storage name. Use `T::data_name("rust_field")`,
  which needs `use typiql::TypiQLType`. `value` is the serde JSON form, so an
  enum is `serde_json::to_value(Status::Done)?` and comes out as `"Done"`, not
  the GraphQL `DONE`.
- **Returning data**: return the generated types (`Task`, `Vec<Task>`) and take
  `TaskInput` for patches. Don't invent parallel JSON shapes.
- **Using the adapter directly**: `ctx.data::<typiql::AdapterMap>()?[T::adapter_name()]`
  with `T::collection_name().into()` as the location, then
  `serde_json::from_value` each row. Do this only when a helper doesn't fit,
  and still publish.
- **Code with no request context** (startup seeding, a background task):
  - Keep a clone of the `Arc<dyn TypiQLAdapter>` you put in the map.
  - Call `adapter.get_many/add/update/remove(T::collection_name().into(), T::key_field(), …)`.
  - Publish `TypiQLBroker::publish(TChanged { … })` yourself.
- **Errors**: return `async_graphql::Error`. typiql's error log (if enabled)
  records hand-written resolvers too.

### One subscription for every type (live-updates hub)

Browsers allow about 6 connections per origin, and each open multipart
subscription holds one of them. A frontend that opens one `xChanged`
subscription per mounted screen can run out of connections and silently stall
other requests.

**No server code is needed.** A single subscription operation can hold several
root fields, each under its own alias. async-graphql runs each root field as
its own stream and merges them onto one connection:

```graphql
subscription {
  a: projectChanged { operationName value { id name } }
  b: taskChanged(id: "…") { operationName value { id title } }
}
```

Each event arrives keyed by its alias, e.g. `{"data":{"b":{"operationName":"add",…}}}`.
Every field keeps its own arguments and its `roles`/`scope` checks. Only plain
root fields are merged this way, not fragments at the root.

The typical-admin frontend library has a client-side service that does this
for you: it combines every mounted component's subscription into one aliased
operation. Use it rather than opening a subscription per screen.

(Optional alternative: a hand-written `#[Subscription]` returning an
`async_graphql::Union` of the `XChanged` types, built by `select_all`-ing
`TypiQLBroker::<XChanged>::subscribe()` streams. That skips the generated
`roles`/`scope` checks, so prefer the aliased operation.)

## Gotchas

- **Recursion limit**: around 25–40 types, rustc fails with
  `overflow evaluating the requirement …` and a `recursion_limit` hint. Add
  `#![recursion_limit = "256"]` at the top of the crate root (`main.rs`/`lib.rs`).
- **`typiql_schema!` placement**: it must see each type's generated
  `{Name}Query`/`{Name}Mutation`/`{Name}Subscription` by bare name. Put it in
  the same module as the types, or glob-import them.
- **Custom roots** passed to `typiql_schema!` must be `#[derive(Default)]`
  structs with an `#[async_graphql::Object]` (or `Subscription`) impl.
- **Don't fake a key**: `getTask` with no arguments returns the first row. Always
  pass `id:`.
- **Read the generated schema** when in doubt. Open `/typiql/playground`, or
  print `build_typiql_schema(adapters).sdl()`, which shows every name exactly.
